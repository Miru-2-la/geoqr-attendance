Database Features

How the schema supports GeoQR Attendance.

Single-Table Inheritance

Admin and Student are represented through the users table using the role discriminator.

Geo-Fencing

Event latitude, longitude and radius determine the allowed attendance zone.

Device Fingerprinting

device_id records the device associated with an attendance submission.

Proxy Detection

Location, distance and device information provide multiple signals for suspicious attendance detection.

Email Uniqueness

Each user email is constrained as unique to prevent duplicate user identities.

Foreign Key Integrity

Event creators are linked to users through created_by.

Database Design Overview

Architecture decisions used in GeoQR Attendance.

01 — User Inheritance

The application uses JPA SINGLE_TABLE inheritance. Admin and Student share the users table and are differentiated through the role discriminator column. This reduces table duplication and simplifies user management.

02 — Geo-Fencing

Each event stores latitude, longitude and radius_meters. During attendance validation, the student's location can be compared against the event location and permitted radius.

03 — Attendance Validation

Attendance stores event_id, student_id, device_id, coordinates, calculated distance, status and timestamp. This creates an auditable attendance record.

04 — Device Verification

device_id provides an additional verification layer. Repeated or suspicious device usage can be investigated for possible proxy attendance.

05 — Logical Foreign Keys

Attendance uses plain Long values for event_id and student_id rather than JPA object relationships. This keeps the entity lightweight and avoids unnecessary joins.

06 — ORM Strategy

Spring Data JPA and Hibernate map Java entities to MySQL. The configured Hibernate DDL strategy is update, while an explicit schema can document the intended database structure.

Constraints & Architecture Notes

users.id, events.id and attendance.id are generated using GenerationType.IDENTITY and act as the primary identifiers for their respective records.
events.created_by references users.id. Attendance stores event_id and student_id as Long values, representing logical many-to-one relationships with Events and Students respectively.
User is the base entity. Admin uses discriminator value ADMIN and Student uses discriminator value STUDENT. Both share the same users table.
email provides unique user identification. password stores authentication information. role enables role-specific access control. device_id and geolocation fields support proxy-attendance detection.
Events store the permitted geographical point through latitude and longitude. radius_meters specifies the allowed boundary. Attendance stores the student's latitude, longitude and calculated distance_meters for verification.
